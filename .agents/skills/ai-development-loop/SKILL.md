# AI Development Loop V1.0

人确定产品愿景、关键取舍和最终体验是否可接受；AI 查证事实，完成研究、设计、开发、客观验证和经验沉淀。按任务风险调整深度，不为流程本身制造额外文档或 Agent。

## 六步闭环

| 阶段 | AI 要做的事 | 继续条件 |
| --- | --- | --- |
| 1. 需求对齐 | 对照已确认的产品愿景、现有能力和边界；仅在目标、范围、架构或验收标准存在关键歧义时提问。 | 明确要解决的问题及是否值得做。 |
| 2. 方案研究 | 先查当前代码、测试与维护文档，再完成开源存在性调查，核实实现机制、维护状态、许可证和适配成本；比较直接复用、局部借鉴和自研。纯文字等无组件选型的任务记录不适用理由。离线或来源缺失时标记研究未完成，不假装已查证。 | 合理性与复用调查有证据和明确结论，才可开始实施 Plan。 |
| 3. 设计 | 优先扩展现有架构和组件。前端先形成覆盖页面、组件、状态的视觉参考与交互设计；后端先明确 API/Event、数据流、持久化与失败语义。核心架构变更交人决策。 | 路径可实现，边界清楚。 |
| 4. 验收设计 | 编码前确定可执行的成功、异常与回归检查，以及机器可读证据。用户可见界面还须规划真实渲染截图与人工视觉验收。 | 完成标准可以独立检查。 |
| 5. 自主开发 | 研究与验收设计通过后形成简明 Plan，写入实施 Issue，再由 Agent 编码、测试/修复、审查并提交 PR；失败在当前需求边界内自行分析修复。 | 所有适用的单元测试与真实运行环境前后端验收通过，证据关联到确切代码版本。 |
| 6. 人工验收 | 交付可体验的结果、测试证据和未验证边界。产品价值、自然感、审美与实际体验由人判断。未通过则在原 Issue 内处理反馈；独立新需求另开 Issue。 | 人明确接受，或反馈进入下一轮。 |

## 执行边界

- 顺序门槛：需求合理性评估 → 仓库与开源调研结论 → 设计及验收标准 → Plan → 实施 Issue → Agent 实现 PR → 客观验收 → 人工接受。已有 Issue 可作为需求来源，但研究未完成不能标为 Ready 或派发实施。研究阶段提出候选方向不等于开发承诺。
- 实施 Issue 必须写清目标、非目标、复用结论及来源、允许改动的模块边界、验收方法和停止条件。Agent 不得自行增加产品能力；发现需要改变这些边界时回到关键决策，明确后继续。
- Online test 必须覆盖真实运行环境的完整链路：前端实际点击、输入和操作关键流程及异常状态，并完成截图对照的视觉验收；后端实际调用 API，检查响应、状态转换、持久化及恢复，并运行相关单元测试。必须核对浏览器与 API 指向同一受测版本，记录环境、commit、命令/操作、结果与证据。Mock、DOM 或单元测试通过不能替代真实前后端联调。
- 缺环境、未执行、失败或跳过的必要检查都不能记为通过，也不能宣称开发完成。纯文档或无某层行为影响的变更可记录该层 N/A 和理由；涉及完整产品流程时不能省略前端或后端。人工体验接受仍是独立门槛。
- 简单变更可在几分钟内完成前四步；重要或跨边界变更才深入研究。不要把阶段变成六份长期文档。
- 已明确的需求、设计和验收条件不逐步请示。仅当关键目标、架构或体验取舍无法从现有决策推定时请人决策。自动测试失败由 AI 自行修复。
- 工作状态可用 `Ready → Developing → AI Verified → Human Review → Accepted` 表达；`AI Verified` 不能代替人工体验验收。
- 每轮收尾检查是否产生了经过验证、确有复用价值的组件、测试、架构决策或 Skill。只沉淀有价值的资产；更新现有归属文档，历史留在 Issue、PR、Git 中。
- 额度必须遵守下文双窗口硬停止；不得为消耗额度创造功能或重构。

## Codex 双窗口额度硬停止

- 每次任务开始、阶段切换和收尾先读真实额度，分别核对5小时（300分钟）与周（10080分钟）窗口；剩余为100-usedPercent，未知/缺失不能视为充足。
- 任一窗口剩余不高于10%时立即硬停止：不继续研究、计划、开发、测试、模型调用、审查、CI轮询、提交或合并，也不开新任务。仅允许一次必要只读额度核对和自有在途进程安全停止；保留未完成状态。不得自动使用重置信用。
- 任一窗口剩余接近15%（约85%已用）时不再开新项，提前收尾，确保至少留10%供用户紧急需求。
- 定时唤醒在触发门槛后只核对额度；两项均高于10%再接续同一交付链。无法取得任一窗口值时不启动自动任务，不猜测。此硬门槛优先于持续开发与已授权自主执行。

## Character Memory 的落点

- 已维护的产品愿景见 `docs/current/DESIGN.md`，架构见 `docs/current/ARCHITECTURE.md`；源码与测试优先于说明文档。用户提出的新愿景措辞若改变既定产品边界，应先作为产品决策确认，不直接覆盖当前契约。
- 遵守仓库 `AGENTS.md`、`CONTRIBUTING.md` 与相关 `docs/current/` 契约。重构前查 `docs/current/TECH_DEBT.md`。Issue/PR 承载任务研究、设计、验收标准与证据；不新增重复的长期 `VISION.md`、`DEVELOPMENT.md` 或根目录 `ARCHITECTURE.md`。
- 任何用户可见前端修改，在实现前必须由用户批准具体参考图并在 Issue 映射页面、组件和状态；实现后按 `CONTRIBUTING.md` 留真实截图和视觉结论。缺参考图时先准备设计并取得批准。
- 核心行为提供可重复、机器可读的检查证据。CI 不依赖 GPU 或模型下载；需要浏览器、真实模型或设备的验证走对应运行环境，并明确未验证边界。
